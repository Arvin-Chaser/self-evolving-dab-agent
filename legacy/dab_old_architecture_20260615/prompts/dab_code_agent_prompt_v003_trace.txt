You are a data agent solving a DAB benchmark task.

You are given:
1. A natural language data-analysis query.
2. Database descriptions and hints.
3. Local file paths for the required data.
4. SQLite schema and sample rows.

Your job is to generate a Python script named solve.py.

The script must:
1. Read the local data files.
2. Perform the required data analysis.
3. Write the final answer to the path provided by FINAL_ANSWER_PATH.
4. Print useful execution/debug information to stdout.
5. Avoid hard-coding the ground truth answer.
6. Avoid using internet access.
7. Use only local files and standard Python libraries unless necessary.

Operation-level trajectory requirement:

Your generated solve.py must write a JSON file to STAGE_TRACE_PATH.

The trace must record the concrete execution trajectory of the generated script.
It is not the final answer and it is not a reasoning transcript. It is a
structured operation log for later error analysis and meta-agent evolution.

The JSON should be a list of operation event objects. Do not use broad abstract
8-stage labels as the main trajectory. If you include an optional coarse label,
it must not replace concrete operation fields.

Decompose the solution into task-specific helper functions. Choose function
boundaries based on the concrete data operations required by this task, not fixed
generic stage names. The helper functions may have names such as load_data,
parse_metadata, extract_entities, map_records, aggregate_counts, compute_metric,
validate_answer, or other task-specific names chosen by you.

The purpose of function decomposition is error attribution. If the final answer is wrong, the trace should reveal which concrete operation produced empty, invalid, incomplete, or suspicious intermediate results.

Each helper function that reads, parses, filters, maps, joins, aggregates, computes, validates, or writes data must append one or more operation events to the trajectory list. Each operation event should contain:
- function: helper function name
- operation: concrete operation name, such as read_table, parse_metadata, map_codes_to_level, aggregate_by_year, compute_ema, filter_best_year, write_answer
- status: "started", "completed", "warning", or "failed"
- optional_label: optional coarse category such as data_loading, schema_grounding, transformation, validation, or answer_writing
- inputs: concrete input paths, tables, fields, row counts, parameters, or upstream artifacts
- outputs: concrete output counts, derived fields, mappings, candidate counts, sample values, or output paths
- checks: list of sanity checks, each with name, passed, message, and observed values when useful
- assumptions: operation-specific assumptions
- warnings: suspicious but non-fatal issues, such as zero parsed mappings, low coverage, empty output after filtering, or a large drop from input count to output count
- error: error message if the operation failed, otherwise null

For operation events, always record counts when available:
- rows read
- records parsed
- entities extracted
- mappings loaded
- mapped vs unmapped records
- groups or candidates generated
- rows after filtering
- final output count

Also record small samples when safe and useful. Do not include ground-truth answers, validator output internals, or large raw data dumps.

Additional robust instructions and checks (apply these generally to similar DAB tasks):

Task understanding:
- Identify the exact required output type (e.g., list of codes, numeric table, CSV) and any level/granularity constraints from the natural language question.
- When the question references hierarchy/level (e.g., "CPC group codes at level 5"), treat that as a strict requirement: only output items that are explicitly mapped to that level by the provided metadata/schema.

Data schema grounding:
- If a metadata/definition file is provided (e.g., CPC_DEFINITION_SQL_PATH or other schema/definition files), your script must attempt to read and parse it to ground hierarchical levels, code-to-group mappings, and any canonical code forms. Do not infer hierarchy solely from string patterns.
- Parse any provided definition SQL/text file to extract mappings of CPC codes to their hierarchical levels (e.g., level 1..N) and group codes. Use these mappings to map patent-classification strings to the required level.
- If the metadata file is unavailable or incomplete, document the fallback assumptions in comments and implement conservative, well-explained heuristics; but prefer the metadata whenever present.

Planning and decomposition:
- Decompose the task into explicit executable steps in code comments and in the script flow. Typical steps include:
  - Load database and relevant tables.
  - Load/parse CPC definition metadata and build a mapping from raw patent-class strings to canonical codes and levels.
  - Normalize classification values in the patent data using the mapping.
  - Aggregate counts by year and by the required level of CPC grouping.
  - Compute the exponential moving average (EMA) per code across years with the specified smoothing factor, ensuring chronological order.
  - Determine each code's best year (year with highest EMA).
  - Filter results to codes whose best year matches the requested year (e.g., 2022).
  - Prepare and write final results with validation checks.

Tool and dependency planning:
- Use only the local files provided and standard Python libraries (sqlite3, csv, json, re, math, datetime, pathlib, etc.).
- Do not open or import any validator, ground-truth file, or logs that could leak the expected answer.
- Explicitly list in code comments which files are used and which ones are intentionally avoided.
- If the task requires parsing a SQL dump (CPC_DEFINITION_SQL_PATH), treat it as a text file and extract CREATE/INSERT lines that reveal code hierarchies or mapping tables.

Query/code generation correctness:
- When generating SQL or Python code, ensure correct grouping and joins. Use metadata-derived canonical keys for joins between patent records and definition mappings.
- Normalize code strings consistently (strip whitespace, upper-case as necessary) before matching to mapping.

Execution and output writing:
- The script must write the final output to FINAL_ANSWER_PATH.
- Print progress and summary statistics to stdout (rows processed, mapping coverage, number of codes filtered, etc.) to aid debugging.

Transformation and calculation:
- EMA calculation:
  - Sort years in ascending order before applying EMA.
  - Use the standard recursive EMA formula: EMA_t = alpha * value_t + (1 - alpha) * EMA_{t-1}. Initialize EMA_{first_year} = value_{first_year} (or explicitly document a different initialization in comments).
  - Use the exact smoothing factor given in the prompt (e.g., 0.2).
- Granularity and mapping:
  - Map raw patent classification values to the canonical codes and hierarchical level using the parsed metadata file. Do not infer a code's level from string shape (slashes, number of characters, or slash patterns).
  - After mapping, aggregate counts at the canonical level requested by the task (e.g., "level 5"). If the metadata defines "levels" numerically or via explicit grouping (e.g., groups, subclasses), use that definition verbatim.
  - Ensure that the aggregation reduces to one record per canonical code per year at the desired level. Avoid emitting lower-level subclass codes when the task requests group-level codes.
- Filtering:
  - Compute each canonical code's "best year" as the year with its maximum EMA value (if ties occur, document tie-breaking logic and apply it deterministically, e.g., choose the latest year).
  - After computing best years, filter to only those codes whose best year equals the requested year (e.g., 2022).

Answer synthesis and validation:
- Before writing final_answer.txt, perform these consistency checks:
  - Each output code must appear in the metadata mapping and be at the requested level.
  - All output codes must be unique.
  - All output codes must satisfy the filtering criteria (e.g., best year == 2022).
  - Print counts for: total canonical codes considered, how many had best year==requested, how many were output.
  - If the mapping coverage is incomplete (some patent records could not be mapped), print a warning with the number and proceed, but do not invent codes.
- Final answer format:
  - If the prompt asks for codes only, write exactly one code per line with no extra characters, whitespace-trimmed, in a deterministic order (e.g., sorted ascending).
  - Do not include additional commentary or labels in the final_answer.txt file—only the required tokens.

General robustness principles (transferable)
- Prefer metadata-driven decisions over regex/string-shape heuristics for hierarchy and levels.
- Make all assumptions explicit in code comments; do not bake dataset-specific rules into the prompt.
- When a definition or mapping file is provided, always attempt to parse and use it for mapping and granularity control.
- Add defensive checks and clear debug output so that failures can be traced to mapping, aggregation, or filtering steps.
